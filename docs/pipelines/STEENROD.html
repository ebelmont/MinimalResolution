The Steenrod Pipeline (mr_st / kos)#

Classical Steenrod-algebra layer of the codebase, built on the generic template framework described in docs/FRAMEWORK.md (matrix<ring>, ModuleOp, CoModule / comodule_generic, Hopf_Algebroid<ring,algebroid>, curtis_table, monomial_index, polynomial<ring>). This document covers only the classical-Steenrod-algebra instantiation of that framework: the files Fp.*, exponents.*, mon_index.* (usage only), steenrod.*, steenrod_init.*, stmain.cpp, kosul.cpp.

1. Purpose#

  • The object being resolved is P = F_p[x_1,...,x_5] (typedef polynomial<Fp>, steenrod.h:10), a polynomial ring on ≤5 generators whose degrees (xnDegs = {0,4,16,52,160,484}, exponents.cpp:31) are 2(p^n-1) for p=3 — i.e. the degrees of the Milnor polynomial generators xi_n of the dual Steenrod algebra A_*. Steenrod_Op equips P with the Milnor coproduct (steenrod.cpp:51-57, see §4), making it a Hopf algebra (a Hopf_Algebroid<Fp,P> with the base ring and the algebroid coinciding — no nontrivial left/right units, steenrod.cpp:81-86).
  • SteenrodInit resolves the trivial comodule F_p (rank 1, degree 0, steenrod_init.cpp:32, via Hopf_Algebroid::set_to_trivial) by an injective/cofree resolution in the category of P-comodules. The ranks and degrees of the resulting cofree comodules (FreeSteenrodCoMod, steenrod.h:99) at each resolution step s and internal degree t are exactly dim Ext_P^{s,t}(F_p,F_p).
  • Resolved: what P actually is, and why it has no exterior part. MinimalResolution.pdf §2 ("Notation") defines, for the BP Hopf algebroid (BP_*, BP_*BP) and the invariant ideal I = (p, v1, v2, ...): P := BP_*BP/I = F_p[t1, t2, ...], and states that P is a sub-Hopf-algebra of the dual Steenrod algebra, isomorphic to the whole thing with degrees doubled only at p=2. This P — generated by the images t_i of BP_*BP's own polynomial generators, not by the dual Steenrod algebra's Milnor generators xi_i directly — is exactly the object steenrod.h's P = polynomial<Fp> models (the code just names its generators x_i/xi_i rather than t_i, and the degree match |v_n| = |xi_n| = 2(p^n-1) noted below is precisely the shared grading of v_i and t_i under the BP_*BP structure maps, not a coincidence). So the earlier framing of P as "a truncation of the true dual Steenrod algebra, missing an exterior part" was imprecise: P = BP_*BP/I is genuinely purely polynomial — it is not supposed to have an exterior part at all, because the exterior generators of the odd-primary dual Steenrod algebra live outside BP_*BP/I's sub-Hopf-algebra. (The maxVar = 5 generator cap, exponents.h:7, is a separate, ordinary degree-range truncation for computational purposes — nothing to do with the exterior-part question.)
  • Per the top-level README and the paper (MinimalResolution.pdf §5, "the complexity of computing a minimal resolution of M/I has smaller order than computing a minimal resolution of M"), this Ext_P(F_p,F_p) computation is the cheap "model" resolution that the BP pipeline's mr_BP lifts into an actual BP_*BP-comodule resolution of BP_* — see docs/ARCHITECTURE.md §5 for the mechanism and the precise sense in which it's valid. exponents.cpp's generator-degree table is reused verbatim by the BP pipeline for v_n (BP.cpp:118 calls total_deg(e,xnDeg)) because v_n and t_n share their grading by construction, not by an unexplained numerical coincidence.

2. Executables#

mr_st (from stmain.cpp)#

  • Build: sh st_compiling → g++ -g exponents.cpp Fp.cpp mon_index.cpp steenrod.cpp steenrod_init.cpp stmain.cpp -std=c++11 -I./ -Wall -Wfatal-errors -O0 -fopenmp -o mr_st (st_compiling).
  • Usage (README, adapted from the BP example at README.md:28-30): ./mr_st <half-of-maxdeg> <resolution-length>
    • argv[1] → maxdeg (stmain.cpp:8): README warning — "the first input parameter is half of t" (README.md:44); the code passes it straight through as maxdeg to SteenrodInit/monomial_index, so the actual internal-degree cutoff used by the program is argv[1], but by the project's convention that value already represents t/2 in the reader's intended grading (this halving convention is asserted only in the README, not visible in stmain.cpp itself).
    • argv[2] → length (stmain.cpp:9): resolution length s, i.e. number of resolution steps.
    • Hardcoded prime: SteenrodInit st(3, maxdeg, length, ...) (stmain.cpp:11) — always p=3 for mr_st in this fork.
  • Input: <maxdeg>_steenrod_coaction.data — the Milnor-coproduct table. If absent, SteenrodInit's constructor (IorO=false default, steenrod_init.cpp:6-20) computes it via make_delta and writes it before reloading; so the first run for a given maxdeg self-generates this file, later runs at the same maxdeg reuse it.
  • Output (all prefixed <maxdeg>_, stmain.cpp:5-6):
    • <maxdeg>_maps — injection/quotient matrices per resolution step (hopf_algebroid/5.h:87-89).
    • <maxdeg>_gens — generator data per step (cofree comodule ranks/degrees).
    • <maxdeg>_BPtables — curtis_table per step, saved for reuse as the "lifting model" by other Hopf algebroids (comment at hopf_algebroid/5.h:46) — this is the artifact the downstream BP pipeline consumes.
    • <maxdeg>_ResTables (SteenrodInit::saveResolutionTables, steenrod_init.cpp:52-57) and <maxdeg>_gens_data (SteenrodInit::save_gens, steenrod_init.cpp:60-70) — redundant/derived dumps of the same tables/generators in a different serialization.
    • stdout: a human-readable summary table of Ext-group ranks by (s,t) via Steenrod_Op::output_resolution (stmain.cpp:19, steenrod.cpp:124-152).
  • Ordering/dependency: none beyond needing (or generating) the ..._steenrod_coaction.data file first; unlike the BP toolchain (BPtab → mr_BP → mr_st/BP-I ordering in README), mr_st here is the self-contained classical-Steenrod computation and does not itself depend on BPtab/mr_BP output.

kos (from kosul.cpp)#

  • Build: sh kos_compile → g++ -std=c++11 steenrod.cpp steenrod_init.cpp kosul.cpp mon_index.cpp Fp.cpp exponents.cpp -fopenmp -Wall -I./ -o kos (kos_compile).
  • Usage: ./kos <maxdeg> <length>, same argument meaning as mr_st (kosul.cpp:44-45).
  • Prime is hardcoded to 2: SteenrodInit st(2, maxdeg, length, ...) (kosul.cpp:47) — unlike mr_st's hardcoded p=3. This looks like a leftover from the pre-fork (p=2) code that was not updated in the p=3 port.   • Output: same <maxdeg>_maps / <maxdeg>_gens / <maxdeg>_ResTables / <maxdeg>_gens_data as mr_st, plus:
    • <maxdeg>_res — the composed resolution differentials (resolution(), inverse.h:47-104).
    • <maxdeg>_splitting<i> — per-step splitting maps (inverse(), inverse.h:33-42).
    • stdout: "success"/"fail" from check_splitting (inverse.h:107-..., called at kosul.cpp:69-71).

4. Data flow / control flow (mr_st)#

  1. Construction (stmain.cpp:11 → steenrod_init.cpp:5-39): SteenrodInit(3, maxdeg, length, "<maxdeg>_steenrod_coaction.data") constructs Steenrod_Op steenrod_oper(maxdeg, 3, &deltaTable) (steenrod.cpp:5-26), which:
    • Initializes Fp_Op(3), P_opers, PP_opers, FpMod_opers, PMod_opers, and mon_index(maxdeg) (then mon_index.init_mon_array() enumerates every monomial up to maxdeg, mon_index.cpp:38-58).
    • Wires itself into the Hopf_Algebroid<Fp,P> base (ringOper, algebroidRingOper, moduleOper, algebroidModuleOper).
    • Builds power_p(i) = prime^i (steenrod.cpp:20-25), used in the coproduct formula.
  2. Coproduct table: if <maxdeg>_steenrod_coaction.data doesn't already exist as a valid prior run, make_delta (steenrod.cpp:49-60) computes, for each generator x_j, the Milnor coproduct Δ(x_j) = x_j⊗1 + 1⊗x_j + Σ_{k=1}^{j-1} x_k ⊗ x_{j-k}^{p^k} (steenrod.cpp:51-56, matches the classical Milnor formula Δ(ξ_j)=Σ_i ξ_{j-i}^{p^i}⊗ξ_i), then extends multiplicatively to all monomials via monomial_index::substitution_table (mon_index.h:42-74), writing the whole table to disk. load_delta (steenrod.cpp:36-46) re-reads it into delta_table as a matrix<P> indexed by matrix_index (monomial index) rather than raw exponent. Steenrod_Op::initialize (steenrod.cpp:92-101) then calls Hopf_Algebroid::init_cofree_data with each monomial's total degree (total_deg(e, xnDeg)), which precomputes the structure needed to build cofree comodules at arbitrary degree shifts (see FRAMEWORK.md).
  3. Trivial start: steenrod_oper.set_to_trivial(comod, 0) (steenrod_init.cpp:32) makes comod the rank-1 comodule concentrated in degree 0 (i.e. F_p itself) — the object to resolve.
  4. Resolution loop: st.resolve(filename) (stmain.cpp:15) calls Steenrod_Op::pre_resolution_tab (inherited from Hopf_Algebroid<Fp,P>::pre_resolution_tab, hopf_algebroid/5.h:51-96), which for i = 0..resolution_length:
    • Calls resolvor(resolved, inj, indj, qut, table[i], new_map, gens[i], ...) (hopf_algebroid/5.h:4-41): embeds the current comodule into a cofree comodule F (embed2cofree), does Gaussian elimination on the injective map to find a splitting (indj->gaussian), and computes the quotient comodule (quotient_p) which becomes resolved for the next iteration (i.e., the next "connected cover"/kernel of the counit map).
    • Saves inj, qut to <maxdeg>_maps, saves F's generators to <maxdeg>_gens, and dumps the curtis_table for step i to <maxdeg>_BPtables — every step's I/O happens inside this loop, so resolution data accumulates on disk incrementally rather than all at the end.
  5. Post-processing: saveResolutionTables/save_gens re-serialize the in-memory ResolutionTables/gens (redundant with step 4's per-step disk writes, but in a single combined file each). Finally output_resolution (steenrod.cpp:124-152) reloads <maxdeg>_gens and prints a (degree × s) rank table to stdout.

5. Koszul alternative (kos)#

  • kosul.cpp reuses the entire Steenrod_Op/SteenrodInit machinery (same steenrod.cpp/steenrod_init.cpp, kos_compile) but starts the resolution from a different comodule and adds a post-hoc consistency check:
    • cofree_double / double_comod (kosul.cpp:8-37) build the "double" of a rank-1 cofree comodule: take the cofree comodule on P itself (rank 1, degree 0, total rank = all monomials up to max_degree), keep only basis elements of degree ≤ max_deg/2, double all degrees, and replace the coaction by its "square" (Stoper->P_opers.multiply(x,x), kosul.cpp:20-21, i.e. the Frobenius/squaring map applied to the coaction). This is set as st.comod (kosul.cpp:50) instead of the trivial comodule that SteenrodInit's constructor would otherwise use.
    • It then runs the same pre_resolution_tab via st.resolve(..., &basis_orders) (kosul.cpp:54), but with basis_orders populated (unlike mr_st, which passes NULL) — these record an explicit ordering of basis elements per step, needed for the inverse/splitting computation below.
    • After resolving, it calls the free function resolution() (inverse.h:47-104, kosul.cpp:61) to compose consecutive injection/quotient maps into the actual resolution differentials (<maxdeg>_res), then inverse() (inverse.h:33-42, kosul.cpp:66) to compute an explicit splitting/inverse of each injective map (<maxdeg>_splitting<i>), then check_splitting() (inverse.h:107ff, kosul.cpp:69) to verify inj and its computed splitting actually compose to the identity, printing "success"/"fail".
  • Relation to mr_st: this is not resolving the same comodule as mr_st. mr_st resolves the trivial comodule F_p (Ext_P(F_p,F_p)); kos resolves the "doubled" cofree comodule built from squaring the coaction on P itself. The name (kosul.cpp = Koszul) and the doubling/squaring construction suggest this is computing (part of) a Koszul-complex-style resolution — plausibly related to the sub-Hopf-algebra generated by p-th powers (ξ_i^p) or to a Frobenius-twisted comodule relevant to the odd-primary Milnor primitives/Koszul dual — used either as an independent structural computation or as a cross-check building block, not as a literal re-derivation of mr_st's output. It additionally performs an explicit numerical self-check (check_splitting) that mr_st does not attempt. Combined with the hardcoded p=2 in kosul.cpp:47 (§2), this strongly suggests kos was not fully carried over in the p=3 fork. Checked against MinimalResolution.pdf: the paper's own §9 source-code walkthrough documents algebra.h through Z2.h/Z2.cpp and never mentions kosul.cpp, "Koszul," or a doubling/squaring construction at all — unlike the ex/ctau + motivic pipelines (docs/pipelines/MOTIVIC.md, docs/pipelines/EX_CTAU.md), whose p=2-only status is explained by the paper's introduction (see docs/ARCHITECTURE.md §6), kos has no corroborating explanation in the paper at all. The questions below remain genuinely open. 6. Open math questions#

Two questions previously listed here are now resolved — see §1: P is literally BP_*BP/I (not a truncation of the full dual Steenrod algebra, and correctly has no exterior part), and mr_st's role is precomputing the "model" resolution mr_BP lifts (docs/ARCHITECTURE.md §5). What remains open:

  • TODO(math): The exact mathematical role of kos's "doubled"/squared comodule construction (§5), and whether kos remains valid/intended for use at p=3 given the hardcoded SteenrodInit st(2, ...) at kosul.cpp:47.
  • TODO(math): Whether/how the degree-halving convention ("first parameter is half of t", README) interacts with the internal grading used by Steenrod_Op/monomial_index — the code itself treats argv[1] as a plain degree cutoff (maxdeg) with no visible halving or doubling, so the "half of t" semantics must be a convention enforced only by the caller's choice of what t means, not by any code in this pipeline.
